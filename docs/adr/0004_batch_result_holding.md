# Bounded per-key opt-in result holding for batch results

Batch inputs and results must stay durable and retrievable until the submitter has them, but [ADR 0003](0003-metadata-analytics-without-transcripts.md) forbids prompts and completions in the metadata store. Submitting a batch is therefore the **explicit opt-in**: the dedicated store persists **both the durable input bodies and the result rows** **outside** `control.sqlite` and outside Analytics (the metadata store stays metadata-only — no prompts there), access is scoped to the key that submitted the job, storage is budgeted (64 MiB per job, 256 MiB per key), reads are **retry-safe** — a `GET` never destroys results, because there is no way to know the client received them — and rows are deleted by an explicit terminal `DELETE` (the retrieval acknowledgement) or by the local TTL of 24 h after the job reaches a terminal status, whichever comes first. The same decision fixes cost accounting for batch: the batch discount exists only at batch level, so per-item **cost for remote (spilled) rows is always unknown** (never prorated, never zero) and counts toward `unknownCostCount`, while locally dispatched items keep their actual configured COGS and observed usage through the existing accounting, and the provider-reported job-level `usage.cost` (gated by `is_byok`) is recorded on the job itself.

**Status:** accepted

**Considered options:** (1) hold results in the metadata DB alongside request rows — rejected: it silently overturns ADR 0003's metadata-only guarantee and puts transcripts in the analytics path; (2) no holding at all, results only inline at completion — rejected: destroying results on response construction cannot know whether the client received them, so a dropped connection would lose the only copy and the surface would be unusable for its async purpose; (3) bounded per-key opt-in store outside metadata, retry-safe reads with TTL, budgets, and explicit `DELETE` purge (chosen). For cost: prorate batch-level `usage.cost` across remote items versus recording per-item cost unknown — prorating invents a number the provider never reports per item, violating the repo-wide "unknown ≠ zero" identity, so unknown wins for remote rows until upstream publishes per-item usage; local rows were never a question, they keep real COGS.

**Consequences:** The store's rows contain input bodies (prompts) and completions on disk — deletion at TTL/DELETE and the per-key budgets are load-bearing, not hygiene. The store is never read by Analytics or the requests ledger; nothing may join from metadata into it, and the metadata store itself still holds no prompts. Reading is safe to retry, so retention (not consumption) bounds the data: terminal `DELETE` is the acknowledgement gesture, and the 24 h TTL is the backstop. Remote per-item accounting rows finalize with tokens when a result body defensively carries `usage`, but their cost stays unknown and is counted as such; local batch items behave exactly like interactive requests in accounting. Job-level `usage.cost` is provider-reported actual, attributed with `is_byok` gating. Reversing this decision later means retracting data already written outside the metadata store, which is why the store is bounded and short-lived by construction.
